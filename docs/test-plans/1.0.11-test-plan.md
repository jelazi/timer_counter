# Manual test plan — Timer Counter 1.0.11+12

Covers `7b32f4e..4cf128f` on `develop` (8 commits, single repo, no local dependency repos): per-context
work schedules / days off / month goals with two new PocketBase collections (`eee84f8`), the sync
ledger, offline queue and auth keep-alive (`c21afb4`), the DST day-counting fix (`b19dab4`), macOS
ad-hoc signing and min macOS 12.0 (`e7a5eaa`, `70020fa`), iOS Swift Package Manager migration and
pods at iOS 15.0 (`87f76c4`, `4cf128f`). Expected results are written for the **fixed** behaviour of
two changes that were not committed when this plan was written (v2 backup restore must keep context
settings; "today" must be a calendar day across DST) — the build under test must contain them.
None of the sync changes has ever run against a live server; sections A–E use a throw-away TEST
server and must pass before section F touches the live server.

Tick a box only when you have seen the expected result yourself.

**Platforms:** 🖥 macOS · 🪟 Windows · 📱 iOS · 🤖 Android · 🌐 Web. Linux has a runner folder but no
build or deploy script and is not covered.

## 0. Before you start (setup, no ticks)

**Servers**
- **LIVE** — the production PocketBase. Before anything else: Admin UI → Settings → Backups → create a
  backup and download it. Write down, per account (`lzizka@gmail.com`, `eli.zizkova@gmail.com`), the
  record count of every collection (filter `user.email = "<mail>"`).
- **TEST** — a separate PocketBase instance, same version as LIVE, **not running on device A** (e.g.
  a second Coolify resource with its own HTTPS subdomain). Import `pocketbase/pb_schema.json`. Create
  users `qa1@…` and `qa2@…`. Superuser access to its Admin UI is needed (rules, token duration, Logs).
- **TEST-OLD** — a second fresh instance with the pre-1.0.11 schema (no context collections):
  `git show 7b32f4e:pocketbase/pb_schema.json > old_schema.json`, import that, create user `qa1@…`.

**Devices**
- **A** — Mac with 1.0.11 under a **separate macOS user** (the app container
  `~/Library/Containers/com.example.timerCounter` is per macOS user; signing your real user into a TEST
  account wipes its local data). If you must use your own user, copy the container folder first.
- **B** — iPhone, iOS Simulator or Android with 1.0.11. Keep the real iPhone (`cz.jelazi.timerCounter`,
  not yet signed in) untouched for section F, or accept that signing it into TEST and later into LIVE
  wipes and re-downloads it.
- **C** — any device or user with **1.0.10+11**, built from `7b32f4e`
  (`git worktree add ../timer_counter_1.0.10 7b32f4e`), for the mixed-build rows. Not on the same macOS
  user as A.
- **W** — a browser with the web build (`flutter build web --dart-define=POCKETBASE_URL=<TEST url>`).

**Test data**
- `qa1`: on A restore any real backup (Settings → Backup & Restore → Restore from Backup), sign in to
  TEST as `qa1`, Settings → Cloud Sync → Upload to Cloud. This gives several hundred entries, i.e. more
  than one 200-record page.
- `qa2`: at least 20 time entries in the current month (start/stop the timer 20 times) and one target.
- Every entry you create during the tests gets a note `QA-<row>` (e.g. `QA-A3`) so you can filter for
  it in the Admin UI (`notes ~ "QA-A3"`) and on the Time entries screen.

**How to observe**
- *Admin UI*: TEST/LIVE `/_/` → collection → filter. *Admin Logs*: Dashboard → Logs, filter e.g.
  `url ~ "auth-refresh"`; the IP column tells A from B.
- *Deletion log*: Settings → Snapshot history & deletion log → "Deletion log" tab. Sync deletions are
  labelled "deleted by sync (reconcile)" or "deleted by sync (live event)".
- *App log* (only where a row asks for it): 🖥 quit the app, then run
  `"/Applications/Timer Counter.app/Contents/MacOS/Timer Counter" 2>&1 | tee ~/Desktop/tc-qa.log`;
  🪟 `flutter run --profile -d windows` (the release exe has no console); 📱 `flutter run --profile`
  or Console.app filtered by `flutter`; 🤖 `adb logcat -s flutter`; 🌐 browser DevTools console.
- *Offline*: phone = airplane mode; Mac/PC = Wi-Fi/Ethernet off. *Server down*: stop the TEST container.
- *Trigger a sync without restarting*: phone = background for 3 s, then foreground; desktop = click
  another app, then back into Timer Counter (resume); or Settings → Cloud Sync → Download from Cloud.

## B. Auth keep-alive, token refresh, re-login, offline start (gap #3) ⚠️
**Why here:** before `c21afb4` the app signed in only at startup and never refreshed its 7-day token; an
app left in the tray silently stopped syncing. `_ensureAuth` (~383-414) now refreshes a token with less

## C. Real-time events against unsent local changes (gap #4) ⚠️
**Why here:** `_acceptRemoteChange` (~1124-1136) now drops a live event for any record with a pending
local change, and `downloadAll` skips remote upserts for such records (~1303). If this is wrong,
either the local edit is overwritten or remote changes stop arriving.
**Preconditions:** TEST; A and B as `qa1`. To keep a change pending while A stays online, set the
`time_entries` **Update rule** on TEST to
`@request.auth.id != "" && user = @request.auth.id && @request.body.notes !~ "QA-REJECT"`
(the server then refuses any edit whose note contains `QA-REJECT`). Restore the original rule
(`@request.auth.id != "" && user = @request.auth.id`) at C6.

## Known gaps
Things found thin in the code or review that ship anyway. Watch for the symptom.

1. **Offline cold start leaves sync half-asleep** (`main.dart` ~229-243, `signIn` ~281-303): if the
   startup sign-in fails, no keep-alive timer runs, the password is not kept in memory and no
   real-time subscription exists. Queued changes go out only on resume or manual sync; if the saved
   token has also expired, nothing syncs until the app is restarted online. *Symptom:* entries made
   after an offline start never reach other devices on a desktop that stays in the tray. Rows B10–B12.
2. **Flush and a direct push of the same record can both create it** (`_upsertRecord` looks up, then
   creates; not atomic). *Symptom:* two server records with the same note; other devices may show the
   older one after later edits. Rows A16, D3.
3. **Context settings sync as one record per context.** Two devices editing different parts of the same
   context (e.g. Monday hours on A offline, a month exception on B) — the last flush wins and the other
   change is lost silently. Rows A14, E2–E4.
4. **Guard-blocked deletions are re-uploaded.** After the guard refuses a mass deletion, the ledger no
   longer treats those records as server-known, so the next sync uploads them again. *Symptom:*
   records deleted in bulk elsewhere come back. Rows J1–J3, D4–D5.
5. **First run of 1.0.11 on any device starts with an empty ledger**, so a record deleted on another
   device while this one was off comes back once. *Symptom:* a deleted entry reappears after the
   upgrade; deleting it again sticks. Rows F8, F12.
6. **Backup restore is not pushed to the server.** On the next sync the server's context settings
   overwrite restored ones, and server records the backup lacks come back. *Symptom:* a restored
   schedule reverts after a resync. Row G10.
7. **"Month: X h/day" does not drop a target that is off today**, although the comment in
   `time_tracking_screen.dart` says it should. *Symptom:* on T2's context day off the figure still
   includes T2's share. Row I15.
8. **A redundant context override cycles oddly**: a context "work" override that the global setting
   later made redundant goes to "off" on the next tap, not back to inherited. No row; seen when repeating I3–I4 after clearing the global day off.
9. **An enabled day with 0 h (start = end) still counts as a work day** for "work days left", so the
   daily need is spread over it. Row I11.
10. **Android release manifest has no INTERNET permission.** *Symptom:* sync fails only in release APKs.
    Row K13.
11. **`windows/installer/timer_counter_setup.iss` still hard-codes 1.0.10**; `deploy_windows.bat` uses
    `inno_setup.iss` with the pubspec version. *Symptom:* an installer built from the other script
    reports 1.0.10. Row K14.
12. **Sync diagnostics are console-only** (`debugPrint`); a Windows release exe shows none. Rows marked
    "app log".
13. **Rows G7, H3, H6, H7 fail on a HEAD-only build** (`4cf128f`); they need the uncommitted v2-restore
    and calendar-day fixes.
